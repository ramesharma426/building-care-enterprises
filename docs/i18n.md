# Bilingual content (English / Nepali)

## How it's wired

- English lives at unprefixed paths: `/`, `/about`, `/products`, `/products/[category]`, `/contact`.
- Nepali lives at the same paths under `/ne`: `/ne`, `/ne/about`, etc.
- `src/lib/site.ts` exports `LOCALES = ["en", "ne"]`, `LOCALE_PREFIX`, and `LOCALE_TAG` (BCP-47 tags `en-NP` / `ne-NP` used for `hreflang` and `html[lang]`).
- `src/lib/paths.ts` has two helpers:
  - `localeHref(locale, path)` — build a link to `path` in a given locale. Use this everywhere you render a `<Link>`.
  - `counterpartHref(pathname)` — given the *current* pathname, return the equivalent path in the other locale. Used only by the language switcher (`src/components/Header.tsx`) so switching languages keeps you on the same page instead of bouncing to the home page.

See [architecture.md](./architecture.md#route-structure-why-two-route-groups) for why this is two route groups rather than Next's `app/[lang]/` convention.

## The dictionary system

All UI copy lives in `src/dictionaries/en.ts` and `src/dictionaries/ne.ts`, typed against the shared `Dictionary` interface in `src/dictionaries/types.ts`. Both files end with `satisfies Dictionary`, so TypeScript will refuse to compile if the two languages' shapes ever drift apart (a key added to one and not the other is a build error, not a silent missing string at runtime).

`src/lib/dictionary.ts` exports `getDictionary(locale)` to fetch the right one.

**Adding a new string:** add the key to `Dictionary` in `types.ts` first, then fill it in both `en.ts` and `ne.ts` — TypeScript will point at whichever file you forgot.

**Adding a new page:** write the view in `src/views/`, add its copy under a new top-level key in `types.ts` + both dictionaries (following the existing `about`/`contact`/etc. shape), then add the `meta.<page>.title` / `.description` pair used by `generateMetadata()`.

Business *facts* (phone, address, category slugs) are **not** in the dictionaries — they're locale-agnostic and live in `src/data/business.ts` instead. Only translated *copy* belongs in the dictionaries. See [content-editing.md](./content-editing.md).

## Nepali content review

The Nepali copy in `src/dictionaries/ne.ts` was drafted by an AI assistant, not a native speaker. It's internally consistent (mirrors the English structure and meaning exactly, key for key) but **has not been proofread by a native Nepali speaker**. Before launch, have someone fluent read through `ne.ts` — pay particular attention to:

- Business/formal register consistency (the draft aims for polite formal Nepali throughout).
- The registration/legal line in `footer.registeredNote` and `about.trustItems` (numbers and terms like "फर्म दर्ता" should be double-checked against how the firm's own paperwork phrases them).
- Any category `highlights` — these are generic placeholder phrasing and will need rewriting anyway once real product data replaces them (see [content-editing.md](./content-editing.md)).

## `<html lang>` and hreflang

Each route group's `layout.tsx` sets `<html lang="en">` or `<html lang="ne">` directly (see [architecture.md](./architecture.md)). Every page's metadata (via `buildMetadata()` in `src/lib/metadata.ts`) emits:

```html
<link rel="canonical" href="https://buildingcare.com.np/about" />
<link rel="alternate" hreflang="en-NP" href="https://buildingcare.com.np/about" />
<link rel="alternate" hreflang="ne-NP" href="https://buildingcare.com.np/ne/about" />
<link rel="alternate" hreflang="x-default" href="https://buildingcare.com.np/about" />
```

This is what tells Google "these two URLs are translations of each other, serve the right one per searcher" — it's the main SEO reason the EN/NE split needs to be systematic (same `path` argument passed to `buildMetadata()` from both twins) rather than ad hoc.
